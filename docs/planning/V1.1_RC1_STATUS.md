## Closeout decisions

### 1. Cancellation capability

Current product solve execution is synchronous. RC.1 therefore exposes **no active
Cancel command** and does not claim cooperative cancellation. Inspector status/tooltips
state the limitation explicitly. A future Cancel feature must introduce a real safe
solver boundary, preserve committed state, and leave no partial document mutation.

### 2. Exact-HEAD automated/native gates

A change to this ledger intentionally triggers all RC-critical suites on the same HEAD:

- macOS arm64 Debug + Release build/CTest,
- macOS GUI application acceptance,
- CAD + FEM topology selection verification,
- hosted selection and persistent-scope contract,
- trusted self-hosted macOS native validation,
- macOS UI visual audit.

A commit whose message contains `[rc-closeout]` additionally runs the standalone GUI
bundle/dependency/signing audit. RC.1 automated closeout is qualified only if every
applicable gate on the containing commit completes `success`.

### 3. Meshing roadmap consistency

Production strategy is the **original Dynamics26 meshing engine**. M1 robust geometry
is QUALIFIED and M2 is AUTHORIZED with M2.0 reference architecture/experiment planning
first. Gmsh/Netgen/TetGen/CGAL/MMG remain clean-room research, architecture,
failure-mode and benchmark references, not production mesher dependencies.

### 4. Physical USER VALIDATED gate

Automation cannot close this gate. Before RC.1 is declared released, a real Mac user
must validate at minimum:

- pointer/mouse/trackpad selection and context authoring,
- keyboard focus/tab/shortcuts,
- Light/Dark readability,
- Named Selection → Fixed Support / Force workflow,
- mesh/preflight/solve/results flow,
- save/reopen and Undo/Redo behavior,
- diagnostics navigation and unsupported-capability wording.

Until that is recorded, `DYNAMICS26_GUI_MILESTONE` remains `1.1.0-beta.3` and RC.1
must not be described as fully released.

## Physical UI feedback hardening — 2026-09-05

The final RC.1 shell package is intentionally narrow and closes the reported usability
issues without opening a new UI-development phase:

- Diagnostics is splitter-collapsible, has an in-panel collapse control and no longer
  forces the application window to grow vertically.
- New/Open/Save remain in the native File menu and are removed from the application ribbon.
- The application ribbon now exposes Geometri / Malzeme / Mesh / Analiz / Sonuçlar;
  the second row remains the context-specific tool surface.
- Navigator / Details / Diagnostics visibility controls are compact icon-only controls.
- Named Selections folder stays in Geometry selection context so CAD Body/Face/Edge/Vertex
  selection tools remain available during authoring.
- Analysis objects support right-click `Pasife Al` / `Aktifleştir`; the old
  user-facing `Bastır` terminology is removed from this command surface.

After this package, UI work is frozen except for defects that block engineering use.
Development priority returns to solver, meshing and CAE infrastructure.

The containing commit is the final RC.1 shell-ergonomics exact-HEAD acceptance trigger;
all hosted/native/topology/selection/visual/bundle gates must attach to this same HEAD.
The acceptance source includes the concrete CommandRegistry definition so the shell
contract assertions compile on both hosted and trusted macOS builds.

## Force arrow density correction — 2026-09-06

Physical feedback rejected the five-arrow display as too sparse. This supersedes the
earlier sparse-glyph presentation decision, not the Total Force engineering semantics.
Each resolved CAD Face is now sampled independently in a local frame from actual QUAD4
facet edges. A regular row/column grid selects real facet centers: up to 20 bins along
the long direction and at least four along a nonzero short direction (maximum 20x20).
Coarse meshes retain their available facet centers; no fake engineering entities are
created. All load arrows have equal length; the larger central arrow is removed.
The 20x4 long-face benchmark renders 80 arrows instead of five, with bounded sampling
on finer meshes. Support glyphs retain their previous sparse policy.

The independent C++ test now has 44 checks, including 20x4 regularity under refinement,
rotated faces, coordinate-scale changes and the 400-arrow cap. Native interaction tests
inspect actual transformed VTK vertices on 1x1, 4x4 and 20x4 faces for all signed XYZ
directions, equal lengths, zero force and suppression/Undo. Visual capture now rejects
the previous five-arrow field and requires a dense top-face display in Light and Dark.
Changing the expected count is required by this explicit physical-user correction;
the scope, direction, real-surface anchoring and zero-force assertions are retained.

Research reference: [VTK vtkGlyph3D](https://vtk.org/doc/nightly/html/classvtkGlyph3D.html)
documents independent per-point vector orientation and scalar scaling. The existing
per-point orientation is preserved; only seed selection and uniform display scale change.
No solver, nodal-load integration, document persistence or Undo semantics change.
USER VALIDATED remains unchecked; exact containing-commit CI must be verified anew.

## Scope boundary

RC.1 does not add arbitrary B-Rep volume meshing, new material formulations, follower
pressure, general contact product solve, arc-length/Riks, or cooperative cancellation.
Those capabilities require their own research/verification gates.
