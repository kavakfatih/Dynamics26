# FEMCAE V0.1.1 — Mimari ve Kaynak Kod Denetimi

**Denetim tarihi:** 29 Ağustos 2026  
**Kaynak:** `FEMCAE-v0.1.0-source-macos-arm64` tabanı  
**Çıktı:** `FEMCAE-v0.1.1-source-macos-arm64`

## 1. Sonuç

V0.1.x foundation katmanında V0.2 geliştirmesini durduracak bir matematik veya mimari çökme problemi bulunmadı.
Residual işaret konvansiyonu, Voigt sırası, engineering shear yaklaşımı, trial/commit/revert state semantiği ve GUI ↔ solver C API sınırı birbirleriyle uyumludur.

V0.1.0 paketi derlenebilir ve testleri geçer durumdaydı; V0.1.1 ile release engineering tarafında eksik kalan kontroller güçlendirildi.

## 2. Kapatılan bulgular

### A-01 — macOS architecture kontrolü gerçek gate değildi

Önceki workflow yalnızca `file` komutunun çıktısını yazdırıyordu. Binary yanlış mimaride üretilse bile bu adım başarılı olabilirdi.

**Düzeltme:** `uname -m == arm64` ve `file -L ... | grep arm64` kontrolleri fail gate yapıldı.

### A-02 — Native CI yalnızca Release çalıştırıyordu

Debug runtime checks kaynak seviyesinde yararlı olsa da hedef macOS ortamında çalışmıyordu.

**Düzeltme:** CI `Debug` + `Release` matrisine geçirildi; Debug konfigürasyonunda Fortran runtime checks etkin kalır.

### A-03 — Install edilen API CI'da doğrulanmıyordu

In-tree C testinin geçmesi, install sonrası public header/library düzeninin doğru olduğunu tek başına garanti etmez.

**Düzeltme:** CI install staging ve installed C consumer smoke testi eklendi.

### A-04 — Hata yollarının test kapsamı zayıftı

Foundation testleri ağırlıklı olarak başarılı akışları kontrol ediyordu.

**Düzeltme:** `unit_error_paths` eklendi. Boyut uyuşmazlığı, sıfır vektör, initialize edilmemiş state ve invalid state index senaryoları kilitlendi.

### A-05 — Tolerance metadata doğrudan test edilmiyordu

**Düzeltme:** `unit_tolerances` eklendi.

### A-06 — Sürüm planı iki aşamada fazla genişti

Eski plan:

- V0.10: mixed `u-p` + incompressibility + contact + friction
- V0.11: CAD + sections + meshing + full pre/post

Bu paketler birbirinden farklı numerical verification ve GUI/integration riskleri taşıdığı için tek release'e fazla yük bindiriyordu.

**Düzeltme:** roadmap aşağıdaki şekilde ayrıldı:

- V0.10 — Mixed `u-p` / Incompressibility
- V0.11 — Contact / Friction
- V0.12 — CAD / Geometry / Sections
- V0.13 — Meshing + Full Pre/Post Integration

## 3. Korunan temel sözleşmeler

Aşağıdaki konular V0.2'de değiştirilmemelidir:

- `R = f_ext - f_int`
- `K_T Δu = R`
- Voigt: `XX, YY, ZZ, XY, YZ, XZ`
- stress shear = tensorial
- strain shear = engineering shear
- persistent entity ID ile solver equation index ayrımı
- trial/commit/revert state semantiği
- result location metadata
- matrix symmetry/definiteness metadata
- consistent-unit core policy
- Fortran derived type'ların Qt/C++ tarafına doğrudan açılmaması

## 4. V0.2 öncesi açık release gate'ler

### G-01 — Native macOS/arm64 CI

Workflow hazırdır ancak gerçek GitHub repository üzerinde çalıştırılmalıdır.
Bu denetim sırasında bağlı GitHub hesabında erişilebilir bir `FEMCAE` repository bulunamadı; bu nedenle native workflow run burada tetiklenemedi.

### G-02 — Açık kaynak lisansı

Paket içinde `LICENSE` yoktur. Bu bilinçli bir karardır ancak public open-source release öncesinde mutlaka kapatılmalıdır.
Lisans seçilmediği sürece kaynak kod teknik olarak açık kaynak lisanslı değildir.

### G-03 — Project adı / repository adı

`FEMCAE` çalışma adı kullanılabilir, ancak public repository açılmadan önce kalıcı adın kesinleştirilmesi önerilir; sonradan header namespace, bundle identifier, C API prefix ve dokümantasyon migration'ı maliyetlidir.

## 5. V0.2 için zorunlu tasarım hedefleri

V0.2'de ilk kod yazılmadan önce aşağıdaki veri yapıları birlikte tasarlanmalıdır:

- `Node` storage ve persistent ID lookup,
- element connectivity,
- `FieldRegistry`,
- `DOF` descriptor,
- constraints,
- deterministic equation numbering,
- local coordinate frame,
- material/section references,
- analysis model ownership/lifetime.

Ana kural:

```text
Node ID != Array Index != DOF ID != Equation ID
```

Pressure alanı gerçek mixed elementlerden önce sisteme girmelidir. Aynı şekilde rotational DOF'lar beam/shell gelmeden önce field/DOF modelinde temsil edilebilir olmalıdır.
